# HTC 现状审查与产品方向建议

日期：2026-09-30

状态：只读代码审查和合成数据验证后的建议，尚未批准为新实施计划。
本报告不关闭 FR-006，不替代 M1 最终候选的独立审查，不授权真实安装或历史导入。

## 1. 结论

现有代码已经建立了用户级记忆治理和运行基础，但尚未实现完整的连续理解体验。
主要差距不在于缺少另一个安装器、数据库或宿主适配器，而在于：

- 自然语言输入如何成为有来源、时间和主体的可靠记忆。
- 过去、当前状态、未来意图以及用户表达的意义如何关联和更新。
- 换一种说法、连续追问或询问历史时，如何正确想起相关信息。
- 如何把时间、有效性、结果和表达授权完整交给回答模型。
- 如何验证最终回答，而不只验证数据库字段和接口返回值。

建议保留现有 Python Core、SQLite、daemon、客户端、安装器和 Workbench。
调整接下来的交付重心，不需要整体重写。

## 2. 审查边界

- 阅读产品定义、参考轨迹、运行架构、Work 状态和当前工作树。
- 沿候选提取、准入、合并、纠正、召回、模型上下文及 Workbench 治理路径检查。
- 使用 SQLite `:memory:` 和独立临时目录验证。
- 所有下文人物、地点、情绪和计划都是合成测试输入，不是用户记忆。
- 不读取真实 HTC 记忆数据库，不读写 Codex 会话数据库或 rollout。
- 不修改业务代码、宿主配置、真实运行时或既有 Work。
- 这是产品对齐审查，不是全库无缺陷保证，也不是一次真实多日聊天验收。

## 3. 已有能力

| 层次 | 已有实现 | 距离目标的差距 |
| --- | --- | --- |
| 运行基础 | daemon 单写者、RPC、幂等、离线队列、安装回滚代码 | 当前聊天召回不可用；真实全局安装未执行 |
| 输入 | Hook、结构化 proposal、导入基础 | 默认不捕获原文；自然语言提取依赖关键词；MCP 兜底只有读取能力 |
| 治理 | Candidate 审核、来源、版本、权限、纠正、逻辑撤回 | 人工逐条审核负担高；物理删除和存储安全仍有缺口 |
| 时间与意图 | 部分相对日期锚定、意图状态机、结果未知 | 输出丢失时间和状态；历史查询与当前查询没有分离 |
| 召回 | 用户级权限、文字匹配、短期召回包、撤销检查 | 缺少语义召回、关系扩展和完整的时间视图 |

| 回答 | 将安全投影交给宿主模型 | 没有独立、完整、可测的回答生成与交付前检查链路 |

## 4. 已复现的代码问题

### R1：敏感候选合并后可能失去敏感级别

优先级：P1。置信度：高，已经通过 Core 和 WorkbenchService 两条调用路径复现。

合成输入：一条普通的面试记录，合并一条 `personal` 候选，并把新摘要改为
“面试失败后很难过”。

结果：合并后的 Memory 仍为 `normal`，正文进入 `allowed_memories`。
同样内容创建新 Memory 时会被归为敏感信息，因此合并绕过了该分类保护。

依据：[合并逻辑](D:/dev/darkingtail/human-temporal-continuity/core/src/htc_core/core.py:255)
仅更新摘要、时间、来源及部分权限，没有合并敏感分类。

建议：合并和纠正必须重新检查敏感级别、证据与权限；默认保留更严格限制，
不能把用户确认内容合并等同于用户授权扩大表达范围。

### R2：时间和计划结果在交给模型之前丢失

优先级：P1。置信度：高，已复现。

合成输入：2030-07-18 说“明天去海边”，Core 正确存为预期 2030-07-19。
2030-07-20 召回时，模型只获得摘要“明天去海边”，没有原始时间锚点或绝对日期。
把意图标记为完成后，模型仍得到相同摘要，没有 `completed` 或完成时间。

依据：[模型投影](D:/dev/darkingtail/human-temporal-continuity/core/src/htc_core/core.py:936)
只输出 `memory_id` 和 `summary`；Hook 再次只渲染摘要。

建议：设计版本化的回答上下文契约，传递必要的类型、事件时间、有效期、预期时间、
意图状态、结果证据及不确定性，并生成不会误导当前时刻的表述。
不是把未授权的完整内部审计数据交给模型。

### R3：主动提及频率限制同时阻断明确追问

优先级：P1，属于现有策略与目标的冲突。置信度：高，已复现。

同一合成记忆，在同一会话第 1、2、4、7 轮明确查询：

| 轮次 | 返回记忆数 | 原因 |
| --- | --- | --- |
| 1 | 1 | 正常 |
| 2 | 0 | 未达到三轮间隔 |
| 4 | 1 | 正常 |
| 7 | 0 | 已达到每会话两次上限 |

依据：[召回限额](D:/dev/darkingtail/human-temporal-continuity/core/src/htc_core/core.py:837)。
现有测试也明确要求此行为。

建议：分离“内部获取依据”“用户明确询问”和“AI 主动提起”的计数与授权。
频率限制应抑制重复主动提及，不能直接使用户自己的问题失去回答依据。
明确询问仍必须遵守隐私、撤销和用途限制。

## 5. 已复现的产品能力缺口

### G1：普通自然表达和同义问法无法稳定进入记忆链

候选提取对“某人是我的大学室友”“我想学钢琴”等输入返回空列表。
合成记忆写入“我养了一只名叫团团的猫”后，查询“团团”命中，
查询“我家宠物叫什么名字？”未命中。

依据：[关键词提取](D:/dev/darkingtail/human-temporal-continuity/core/src/htc_core/codex_adapter.py:67)
及[文字片段召回](D:/dev/darkingtail/human-temporal-continuity/core/src/htc_core/core.py:814)。
这是已声明的规则版 MVP 限制，不应包装成已经实现语义理解。

### G2：历史、当前状态与主体关联没有形成统一的回答视图

合成旧状态“我住在南京”被 supersede，新状态为“我住在苏州”。
问“我以前住在哪个城市？”时，只返回新状态。旧状态仍在存储中，
但普通召回只枚举当前记忆。

另外，独立设置的 current state 可以在 Workbench 查询，
并不会自动进入回答用的 RecallPackage。实体别名及 lived context
也没有参与当前召回算法。

依据：[当前记忆查询](D:/dev/darkingtail/human-temporal-continuity/core/src/htc_core/repository.py:404)
和[召回入口](D:/dev/darkingtail/human-temporal-continuity/core/src/htc_core/core.py:792)。

需要区别“曾经为真但后来变化”与“从来不是真的错误记录”。
历史查询可以使用前者，不能复活后者；引入当前状态也必须有可见、可撤销的授权。

### G3：敏感话题确认没有闭环

已保存的敏感合成经历，即使用户直接表示愿意谈该经历，
且允许该 Memory 主动表达，召回仍只返回泛化确认提示，不提供获准的内容。

依据：[敏感分支](D:/dev/darkingtail/human-temporal-continuity/core/src/htc_core/core.py:861)。
当前没有可供该路径消费的单次、单对象表达确认。

需要实现显式确认的消费和撤销，而不是简单取消保护，
也不是每一轮重复询问用户愿不愿意谈。

### G4：尚未证明“自然对话后，下一次实际回答更准确”

MCP 仅有状态、候选索引、召回三个工具。
默认候选原文捕获关闭；开启后仍需治理确认。
所以“有 MCP 工具”和“说过的话已经被记住”并不是同一件事。

现有测试覆盖了不少核心约束，但大多直接构造 proposal 或 Memory，
没有验证所有自然话语经提取、合并、召回、模型生成后的实际回答。
Stop 路径只保存回答哈希，不是交付前的事实或敏感输出检查器。

真实个人使用前还需处理物理删除、静态数据保护和本地控制面的访问保护；
目前的逻辑撤回不能声称已经擦除了原文。

## 6. 推荐产品形态

建议定义为：**以聊天为体验入口、以用户级记忆核心为能力、以 Workbench 为控制面的
个人连续理解系统。**

三个部分各司其职：

1. 日常聊天入口：正常交流，必要时自然确认“记住、纠正、忘记、这次可以谈”。
2. HTC Core：保存带证据的过去、当前有效状态、未来意图和用户明确表达的意义。
3. Workbench：需要时查看、修改、解释和控制；不要求每次倾诉后整理数据库。

第一参考入口建议使用可控的薄聊天验证端或能控制完整请求链的适配器。
不重做完整通用聊天平台，也不把 Workbench 主页面改成陪伴聊天。
Codex 继续作为一个接入端，但不能把所有宿主行为都假设为可由 HTC 控制。

## 7. 最小实现路径

### A. 先固定可验收的行为

复用现有多日参考轨迹，增加换说法、历史查询、纠正、连续追问和授权后的敏感话题。
每个场景同时规定应记住什么、应回答什么、不能推断什么。

增加无 HTC 的对照回答。不能只看模型语气变得亲切，要看是否使用了正确依据。

### B. 修复已有链路

先处理 R1-R3，补齐 RecallPackage 的时间、状态和证据投影。
补上单次敏感表达授权，以及历史查询与当前查询的区分。
为每个修复建立针对性回归，不扩大到无关重构。

### C. 引入语义候选和记忆整合

模型读取当前消息及受授权的短期上下文，输出受结构约束的候选：
主体、命题、类型、原文证据、时间、话语作用域、置信度、敏感级别、
建议新增或关联的对象。

模型提议不是事实。Core 验证证据和权限，决定新增、补充、历史变化、
纠正错误或保留冲突；不能让模型直接覆盖数据库或授予自己权限。
未来事项需要保留承诺程度：愿望、可能性、已决定的计划不能混为一谈，
更不能因为日期已经过去就推断完成。

记忆不要收敛成一份持续覆盖的“用户画像”。保留有来源的具体对象，
通过有限关系连接人物、事件、影响和意图；摘要只作为可重建投影。
先复用 SQLite，不要求引入独立图数据库。

### D. 按当前问题构建回答依据

解析当前问题涉及的主体、时间和意图；结合结构化过滤、关键词和语义候选检索，
再按相关性、当前有效性、授权与信息预算选择。

区分当前事实、历史事实、未完成计划、已知结果、暂定理解以及未知事项。
检索到旧内容不表示它仍然有效，也不表示现在适合说出口。

### E. 验证实际交付的回答

在可控入口中，生成前取得受约束上下文，交付前检查权限版本、明确事实与时间、
不支持的推断和敏感表达。发现冲突时重新生成或澄清。

现有宿主若只允许上下文注入，就明确标注其保证边界，
不能把提示词要求称为强制输出拦截。

自然语言层面的“理解”无法承诺任意输入百分之百正确；
可承诺的是可追溯、可纠正、知道哪些未知，并用持续评测暴露错误。

### F. 降低使用负担，但保留用户决定权

首先验证少量显式选择、非敏感的数据，不全量导入旧聊天。
可以提出按类别授权低风险候选自动准入，但这需要用户另行决定，
不能擅自把现在的逐条治理改成自动接受。
敏感、冲突和缺乏证据的解释仍需自然确认。

## 8. 推荐下一阶段

下一阶段应是一个“过去、现在、未来连续理解”的垂直切片：

- 一个用户、一个可靠聊天入口、多个分开的会话。
- 一段过去经历、一条当前变化、一项未来计划及其后续纠正。
- 隔日、换说法、连续追问后，实际回答仍正确。
- 没有记录或存在歧义时，诚实说明或进行必要澄清。
- 禁止提及、撤回或删除后，不再通过新召回恢复受限内容。
- 普通工作话题不主动翻出敏感往事。

M1 是部署工作，先补齐失败调查和独立审查，保留已有成果。
建议在体验切片成立前不继续扩展第二宿主、云同步、复杂图谱或装饰性界面。
这是优先级建议，不是本报告已经暂停或修改了现有 Work。
